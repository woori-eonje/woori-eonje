# 백엔드 v2 백로그

MVP(v1)에서 **계약상 모든 엔드포인트 + 추천 엔진 + 인증 + 스케줄러**는 구현 완료.
이 문서는 그 다음(v2)에 할 것들을 우선순위로 정리한다. 각 항목은 "왜 v2인가(미룬 근거)"를 함께 적는다.

> 분류: **Tier 0 = 완성도(사실상 곧 해야 함)** · **Tier 1 = 2차 도메인 기능** · **Tier 2 = 확장(트래픽/참여자 커질 때)**

---

## Tier 0 — 프로덕션 완성도 (기능 외, 우선)

v1은 "기능 구현 완료"이지 "프로덕션 완성"은 아니다. 포트폴리오로 "실제 동작 + 탄탄함"을 보이려면 이게 먼저.

| 항목 | 내용 | 왜 지금 안 했나 |
|---|---|---|
| **배포** | api → Railway/Render(스케줄러 때문에 상시가동), db → Neon, 운영 env(JWT_SECRET·CORS 도메인·WEB_BASE_URL), 마이그레이션 배포 | 로컬 기능 우선. **가장 임팩트 큼**(동작하는 URL) |
| **통합/e2e 테스트** | supertest 로 핵심 경로: 인증, 모임생성, 비회원 참여 풀플로우, **확정 동시성**, 소유권 가드. 현재 순수함수 단위(18)만 있고 서비스/엔드포인트는 수동 curl 검증뿐 | 슬라이스마다 리뷰어가 반복 지적한 부채. 테스트 인프라(테스트 DB/트랜잭션 롤백) 셋업 필요 |
| **CI** | GitHub Actions: lint·test·build·prisma migrate 체크 | 배포와 함께 |
| **전역 ValidationPipe + DTO** | 현재 서비스 내 수동 검증 → `class-validator` 데코레이터 DTO 로 선언적 전환(또는 Zod) | 단일 필드 검증에 파이프 인프라 도입은 과하다 판단(§2). 엔드포인트 늘며 수동 검증 중복이 쌓임 |
| **운영 디테일** | 헬스체크 엔드포인트(`/health`), graceful shutdown, `main.ts` `bootstrap()` floating-promise 정리 | MVP 범위 밖 |
| **구조적 로깅** | pino/nestjs-pino + 요청 ID(correlation id), 에러 로깅 표준화 | 기능 우선 |
| **계약 보강** | openapi 응답코드 전수 점검(현재 confirm/calendar 등 일부만 401/403/404 보강), `Empty`/공통 응답 정리 | 점진적 |

## Tier 1 — 2차 도메인 기능 (기획서가 명시적으로 미룸)

`docs/domain.md` MVP 범위 경계 + 기획서 "2차" 항목.

| 기능 | 백엔드 작업 | 비고 |
|---|---|---|
| **알림** | 응답 마감 임박/확정 알림. 이메일(SMTP) → 카카오 알림톡 → 푸시. **도메인 이벤트 발행**(제출됨·확정됨·마감전환됨)으로 알림을 디커플링 | 스케줄러가 이미 마감 전환을 하니 거기에 알림 훅. 알림톡은 사업자/템플릿 심사 필요 |
| **정기 모임 / 반복 일정** | 모임에 반복 규칙(주간 등) → 회차별 생성. 데이터 모델 확장 | 복잡한 반복 일정은 기획서가 2차로 명시 |
| **장소 투표** | 후보 장소 + 참여자 투표 집계. 시간 추천과 유사한 집계 로직 | 시간 조율과 별개 도메인 |
| **구글 캘린더 OAuth** | 현재 `.ics` 단방향 다운로드 → OAuth 양방향(확정 일정 자동 등록) | OAuth 동의화면·토큰 저장 인프라 |
| **정산/채팅/댓글** | 모임 부가 기능 | MVP 핵심 아님 |
| **지도 API** | 장소 투표와 연계 | 2차 |

## Tier 2 — 확장 (참여자·트래픽 커질 때, 지금은 과함)

기획서가 "Redis·MQ는 2차"라고 명시. 데이터 규모가 작은 MVP엔 DB 캐싱으로 충분.

| 항목 | 내용 | 트리거(언제 하나) |
|---|---|---|
| **추천 재계산 비동기화** | 제출 시 동기 재계산 → 큐(BullMQ 등) + worker. 제출 응답 빠르게, 재계산은 백그라운드. `recommendation_status: PENDING→COMPLETED`(기획서 언급한 확장 경로) | 참여자/슬롯 많아 재계산이 제출 응답을 느리게 할 때 |
| **Redis 캐싱** | `recommendation_results` 조회 캐시, 세션/레이트리밋 저장소 | 조회 트래픽 증가 시 |
| **추천 알고리즘 최적화** | 슬롯·참여자 많을 때 후보 생성/집계 복잡도(현재 O(슬롯×참여자×N)) 점검, 인덱스 튜닝, N+1 제거 | 대형 모임 |
| **분산 스케줄러** | 다중 인스턴스에서 cron 중복 실행(현재는 조건부 UPDATE로 *정확성*은 안전하나 중복 *작업*은 함) → 리더 선출/분산 락 | 인스턴스 다중화 시 |

## 보안/운영 강화 (Tier 0~1 사이, 가치 높음)

| 항목 | 내용 | 비고 |
|---|---|---|
| **Rate limiting** | 로그인 brute-force, 참여자 등록 스팸 방지(`@nestjs/throttler`) | 배포 전 권장 |
| **JWT refresh + 무효화** | 현재 stateless access token(7d)만, 로그아웃이 무상태. refresh token + 로그아웃 시 무효화(블랙리스트/회전) | 보안 강화 |
| **이메일 인증 / 비번 정책** | 가입 시 이메일 검증, 비번 강도 | |
| **invite_token 관리** | 재발급(기존 비활성화)·만료 조정 엔드포인트(도메인 규칙엔 있으나 MVP 미구현) | `docs/domain.md`에 정책 존재 |
| **감사 로그** | `meeting_state_logs` 활용 확대, 접근/변경 로그 | 이미 상태전이는 기록 중 |

## 타입/계약 고도화 (점진적, 학습 노트 #3 참조)

| 항목 | 내용 |
|---|---|
| **타입 codegen (Lv1→Lv2)** | 손으로 쓴 `@whenwe/types`를 `openapi.yaml`에서 `openapi-typescript`로 **자동 생성** → 드리프트 0. 이미 openapi가 SSOT라 승급 경로 열려 있음 |
| **Zod 도입 (Lv3)** | 스키마 1개로 정적 타입 + 런타임 검증. ValidationPipe 대체 |
| **API 버저닝** | `/api/v1/...` prefix |

## 우선순위 한 줄 요약

> **배포(Tier0) → 핵심 경로 e2e 테스트(Tier0) → 알림/이벤트(Tier1) → 비동기 재계산·캐싱(Tier2)**

포트폴리오 관점에서 **"실제 배포된 URL + 동시성/소유권 e2e 테스트"** 까지가 v1.5로 가장 가치 있고, 그 뒤가 진짜 2차 기능이다.

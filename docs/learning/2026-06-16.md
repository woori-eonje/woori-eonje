## 1. 참여자 이원(二元) 식별 모델 — edit_token vs JWT

**무엇**
한 모임의 참여자가 두 종류가 됐다.
- **GUEST(비회원)**: `participant_id + edit_token`(localStorage 저장)으로 식별. 기존 방식.
- **MEMBER(회원)**: 로그인 사용자가 초대 참여 시 `userId`로 계정 연동, `edit_token` 없이 **JWT**로 식별.

그래서 가능시간 제출/조회(`availability`) 엔드포인트가 **인증을 이원화**한다 — `Authorization: Bearer`가 있으면 JWT→userId로 참여자 조회, 없으면 `X-Participant-Edit-Token`으로 조회.

**왜 / 트레이드오프**
- 회원에게도 edit_token을 발급해 기존 경로를 그대로 쓰는 안(변경 최소)도 있었지만, 그러면 **로그인 사용자가 localStorage 토큰에 의존**(기기 바뀌면 유실)해 "계정 연동"의 의미가 반감된다. JWT 인증을 택해 기기 무관하게 본인 응답을 수정할 수 있게 했다.
- "로그인했는데 굳이 게스트로 참여" 케이스는 **백엔드 분기 없이 FE가 토큰을 안 보내면** 자동으로 GUEST가 된다 — 규칙이 "Bearer 있으면 MEMBER, 없으면 GUEST"라 단순함이 유지된다.

**💬 면접 포인트**
"식별 주체가 둘(토큰 vs 계정)이 되면서 같은 엔드포인트가 두 인증 수단을 받게 설계했고, '게스트로 참여' 선택권은 서버 분기가 아니라 클라이언트의 토큰 전송 여부로 넘겨 서버를 단순하게 유지했습니다."

## 2. 멱등 join + Postgres 부분 unique + P2002 경합 복구

**무엇**
회원은 한 모임에 1번만 참여해야 한다. `@@unique([userId, meetingId])`를 걸되, 재참여 시 **에러 없이 기존 참여자를 반환(멱등)**하고 FE가 응답 화면으로 보내 변경하게 했다.

**왜 / 트레이드오프**
- **Postgres는 NULL을 unique로 묶지 않는다** → `userId`가 null인 게스트는 같은 모임에 여러 번 참여 가능(기존 "동일 닉네임 허용" 규칙 유지). 회원(userId 존재)만 제약에 걸린다. 한 제약으로 "회원 1회 / 게스트 다회"를 동시에 표현.
- `findUnique`로 기존 확인 후 `create` 하는 구조는 **그 사이 경합**(동시 더블클릭)에서 두 번째 create가 `P2002`(unique 위반)를 던지고, 전역 예외 필터가 이를 모르면 **500**으로 샌다. → `create`를 try/catch로 감싸 P2002면 **다시 조회해 기존 반환**(멱등 복구). unique 제약의 본래 목적(동시성 방어)을 응답 레벨까지 일관되게.

**💬 면접 포인트**
"부분 유니크(NULL 다중 허용)로 회원/게스트 규칙을 한 제약에 담았고, find-then-create의 경합 구간은 P2002를 잡아 멱등 복구해 동시성에서도 '회원 1회' 불변식이 깨지지 않게 했습니다."

## 3. optional-bearer 패턴 — "조용한 강등 금지"

**무엇**
공개 엔드포인트(초대 참여 등록, 가능시간 제출)가 "로그인이면 회원, 아니면 게스트"로 분기하는 공유 헬퍼 `resolveOptionalUserId(authHeader)`:
- 헤더 없음 / 비-Bearer → `null`(게스트 경로)
- Bearer 있고 검증 성공 → `userId`
- **Bearer 있는데 검증 실패(만료·위조) → 401** (게스트로 강등하지 않음)

**왜 / 트레이드오프**
- present-but-invalid를 조용히 게스트로 떨어뜨리면, 토큰이 만료된 사용자가 **자기도 모르게 익명 게스트로 참여**해 계정 연동이 끊긴다. 클라이언트가 인증을 *의도*했으므로, 실패는 명시적 401로 알려 재로그인/토큰 제거를 유도하는 게 맞다.
- "있으면 검증, 없으면 통과"라 가드(`@UseGuards`)로는 표현이 어색 → 서비스 레벨 헬퍼로 분리해 두 모듈이 공유(중복 제거).

**💬 면접 포인트**
"선택적 인증에서 '토큰 없음'과 '토큰 무효'를 구분했습니다 — 무효 토큰을 게스트로 조용히 강등하면 의도치 않은 계정 분리가 생기므로 401로 명시했습니다."

## 4. 추천엔진 보존형 windows vs 슬롯 전면 블록화 (트레이드오프)

**무엇**
참여자가 "18:00–20:00" 같은 **소요시간 블록** 단위로 선택하길 원하는 UX 요청. 두 길이 있었다.
- (a) **엔진 보존형**: DB는 1시간 슬롯 유지, `GET slots` 응답에 `windows`(연속 N슬롯 묶음 = 블록) 배열을 **추가 제공**. FE는 블록으로 표시·선택, 제출은 블록 내 1h 슬롯들로.
- (b) **전면 블록화**: 슬롯 자체를 N시간 겹침 블록(18-20, 19-21…)으로 저장.

(a)를 택했다.

**왜 / 트레이드오프**
- (b)는 **한 시각이 여러 슬롯에 속한다**(18-20과 19-21 둘 다 19시 포함) → 저장·집계·추천이 꼬이고, 추천엔진의 "1h 슬롯 N개를 묶어 후보 생성"이 무의미해진다. 저장/집계/엔진 전면 재설계 = 큼/위험.
- (a)는 표시 계층(windows)만 추가하고 저장·엔진을 **무손상**으로 둔다. `buildWindows`는 추천엔진과 **동일한 연속성 규칙**(`slot[i].end === slot[i+1].start`)을 써서 "FE가 보는 블록 = 엔진이 점수 매기는 후보 구간"이 정확히 일치한다(두 곳의 결합을 주석으로 명시).

**💬 면접 포인트**
"UX 요구(블록 선택)를 저장 모델 변경 없이 표시 계층 추가로 풀었습니다 — 슬롯을 겹침 블록으로 바꾸면 집계·추천이 다 깨지므로, 1h 슬롯은 유지하고 같은 연속성 규칙으로 파생한 windows만 노출했습니다."

## 5. 트랜잭션 내부 가드로 cascade 응답유실 경합 방어 (#8 PATCH)

**무엇**
모임 수정은 "응답자 0명일 때만" 허용한다. 처음엔 트랜잭션 *밖*에서 응답 존재를 확인하고, 트랜잭션에서 슬롯을 전면 재생성(`deleteMany`→`createMany`)했다.

**왜 / 트레이드오프**
- 가드(확인)와 슬롯 삭제 사이에 **누군가 응답을 제출**하면, 슬롯 `deleteMany`의 `onDelete: Cascade`가 방금 들어온 응답을 **소리 없이 삭제**한다 — "응답 있으면 수정 불가"라는 불변식이 깨진다.
- → 응답 존재 검사를 **트랜잭션 안으로** 옮겨 재확인하고, 있으면 throw해 롤백. 완벽한 직렬화는 아니지만(격리수준 의존) 창이 크게 좁아지고, 같은 코드베이스의 `confirmMeeting`(조건부 updateMany count) 경합 방어 패턴과 정합된다.

**💬 면접 포인트**
"파괴적 연산(cascade 삭제) 전의 사전 검사는 트랜잭션 밖에 두면 TOCTOU 경합으로 무력화됩니다 — 불변식 검사를 트랜잭션 안으로 넣어 같은 원자 단위에서 확인·실행하게 했습니다."

## 6. 상태 기반 수정 제한과 스케줄러 상호작용 (#8)

**무엇**
FE는 수정 조건을 "응답자 0명"만 제시했지만, **상태 가드**(COLLECTING일 때만, 아니면 409 `MEETING_NOT_EDITABLE`)를 추가했다.

**왜 / 트레이드오프**
- 스케줄러가 마감(`responseDeadline`)이 지나면 **응답 0명이어도** COLLECTING→READY_TO_CONFIRM으로 자동 전환한다. 즉 "응답 0명 + 마감 끝난 모임"이 실재한다. "응답자 0명"만 보면 이걸 수정 허용해 **종료된 모임을 미래 마감으로 재오픈**하는 사고가 난다.
- 도메인 문서의 "상태별 액션을 서버에서 강제 제한" 규칙에 맞춰, 응답자 수(필요조건)에 더해 상태(충분조건)를 검사. FE 명세의 빈틈을 백엔드가 도메인 규칙으로 보강한 사례.

**💬 면접 포인트**
"FE가 준 조건(응답자 0명)은 필요조건일 뿐이었습니다 — 스케줄러의 자동 상태전환을 고려하면 상태 가드가 빠지면 종료된 모임이 재오픈되므로, 도메인 상태머신 기준으로 조건을 보강했습니다."

## 7. 비대화형 환경에서 Prisma 마이그레이션 수작성

**무엇**
`prisma migrate dev`는 **대화형 전용**이라 비대화형(에이전트/CI) 환경에서 실패한다. 대신:
1. `schema.prisma`에 제약 추가
2. `migrations/<timestamp>_<name>/migration.sql`을 **손수 작성**(`CREATE UNIQUE INDEX "participants_user_id_meeting_id_key" ...`)
3. `prisma migrate deploy`로 적용(비대화형 OK) + `prisma generate`

**왜 / 트레이드오프**
- 핵심은 **인덱스 이름을 Prisma 규칙과 일치**시키는 것: `{매핑된_테이블}_{매핑된_컬럼들}_key`. 불일치하면 나중에 `migrate dev`가 **drift**로 감지해 재생성하려 든다. 기존 마이그레이션 네이밍을 참고해 맞췄고, `migrate status`로 drift 없음을 확인.
- 운영/팀원 환경엔 **`migrate deploy` 한 번** 실행이 필요(코드만 받으면 DB는 안 바뀜).

**💬 면접 포인트**
"migrate dev가 대화형이라 못 쓰는 환경에선 migration.sql을 직접 쓰고 deploy로 적용했는데, Prisma의 인덱스 네이밍 규칙을 정확히 맞춰야 이후 drift가 안 생긴다는 점이 핵심이었습니다."

## 8. per-slot 집계 ≠ 추천엔진 window 집계 (재사용 판단, #3 히트맵)

**무엇**
응답현황 히트맵(`GET aggregate`)은 "슬롯별 가능/애매/불가 카운트"가 필요했다. "추천엔진의 집계 로직을 재사용하라"는 요청이 있었지만 **재사용하지 않았다**.

**왜 / 트레이드오프**
- 추천엔진 집계는 **window 단위**(연속 N슬롯을 묶어 "참여자별 최악 상태", "한 슬롯이라도 미응답이면 no_response")로 동작한다.
- 히트맵은 **개별 1시간 슬롯 단위**로 "그 슬롯에 각 상태를 찍은 참여자 수"만 센다 — **granularity가 다르다**. 엔진 로직을 끌어오면 의미가 왜곡되므로, `participantAvailability.groupBy([slotId, status])` 직접 집계가 정답.
- "재사용"이 항상 옳은 게 아니라 **집계 단위가 같을 때만** 유효하다는 판단. (`(participantId, slotId)` unique 덕에 groupBy `_count`가 곧 distinct 참여자 수인 점도 활용)

**💬 면접 포인트**
"비슷해 보이는 두 집계의 *granularity*가 다르면(슬롯 단위 vs 구간 단위) 재사용이 오히려 버그입니다 — 코드 중복처럼 보여도 단위가 다른 집계는 분리하는 게 맞다고 판단했습니다."

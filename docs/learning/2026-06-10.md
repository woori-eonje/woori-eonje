## 1. 두 갈래 통합 — "무엇을 기준으로 삼을지" 판단

**무엇**
같은 프로젝트가 두 갈래로 갈라져 있었다 — 원격(프론트 담당자: 디자인+UI, 평평한 단일 Next 앱)과 로컬(나: 백엔드까지 염두에 둔 pnpm 모노레포). git 히스토리상 **공통 조상이 없어서**(merge-base 없음) 단순 머지가 불가능했다.

**왜 / 트레이드오프**
- 항목별로 "어느 쪽이 진실인가"를 따로 판단했다: **구조=로컬**(모노레포 — 백엔드를 둘 자리가 있음), **디자인/UI=원격**(담당자 결과물), **패키지매니저=로컬(pnpm)**.
- 핵심 원칙: **패키지매니저는 "디자인"이 아니라 "구조" 선택**이다. 모노레포 워크스페이스(`workspace:*` 내부 패키지 참조)를 쓰려면 pnpm이 필요 → 구조 결정에 종속된다. 그래서 "원격 것을 가져오되 설치만 pnpm으로".
- 안전장치: 합치기 전에 로컬을 `develop-backend` 브랜치로 푸시해 **백업부터 확보**(force-push로 원격 14커밋을 날리는 사고 방지).

**💬 면접 포인트**
"두 갈래를 합칠 때 통째로가 아니라 *축별로*(구조/디자인/툴체인) 진실의 출처를 나눠 판단했고, 패키지매니저는 디자인이 아니라 구조 결정에 종속된다고 봤습니다."

## 2. 타입 2층 구조 — 계약(contract) vs 화면(view-model)

**무엇**
같은 도메인을 설명하는 타입이 두 개였다.
- 원격 `src/types/meeting.ts` — **화면용**(느슨): 소문자 enum(`available`), `id: string`, **이미 포맷된 표시 필드**(`dateRange: "6.1 — 6.14"`, `when: "6.8 (토) 오후 2:00"`).
- 로컬 `@whenwe/types` — **API 계약용**(엄격, SSOT): 대문자 enum(`AVAILABLE`), `id: number`(DB와 일치), `ApiResponse`/`ErrorCode` 봉투.

해결: **2층으로 분리**한다. **계약 타입**(`packages/types`, 백엔드 소유, 네트워크를 건너는 날것 — ISO 날짜·Int id·대문자 enum) + **화면 타입**(`apps/web`, 프론트 소유, 포맷된 표시 형태) + **경계의 변환 함수(어댑터)**.

**왜 / 트레이드오프**
- **표시 문자열을 계약에 넣으면 안 된다.** 서버는 `startAt`(ISO)만 주고 포맷팅(`"6.8 (토)"`)은 프론트 책임. 이걸 계약에 넣으면 백엔드 계약이 화면 사정에 오염된다.
- 2층은 **팀 분업과 정확히 겹친다**: 백엔드는 계약만 책임, 프론트는 화면+어댑터. 서버 응답이 바뀌면 `@whenwe/types`가 바뀌고 → 프론트 어댑터에서 **컴파일 에러로 즉시 드러남**(모노레포+공유타입의 본전).
- **과하게 짓지 않기**: 화면마다 view-model 타입+매퍼를 강제하면 과한 추상화. → "정신은 2층, 구현은 린". 계약 타입을 직접 받아 가장자리에서 포맷 헬퍼 몇 개로 처리하고, **모양이 진짜 갈리는 곳에서만** view-model을 둔다. 과한 레이어도 똑같이 냄새다.
- **지금은 reconcile 미루기**: UI가 아직 mock 데이터라, 원격 화면 타입을 그대로 두고 대소문자·`pending`(미응답=화면 개념)·`EXPIRED` 변환은 **실제 API 연결 시 한 화면씩** 어댑터에서 흡수. 지금 합치면 기능 이득 없이 코드만 흔들림(YAGNI).

**💬 면접 포인트**
"전송 계층(DTO)과 표현 계층(view-model)을 분리하고 경계에 어댑터(anti-corruption layer)를 뒀습니다. 표시용 포맷 문자열이 API 계약에 새어 들어가지 않게 한 게 핵심이고, 다만 규모에 맞춰 매퍼를 남발하지 않고 린하게 유지했습니다."

## 3. 타입 설계 수준 — 드리프트와 "단일 SSOT에서 생성"

**무엇**
타입 설계를 수준별로 정리.
- **Lv0** 각자 타입 → 드리프트가 런타임에 터짐.
- **Lv1** 손으로 쓴 공유 계약 + 화면 변환 → 드리프트가 *컴파일*에 잡힘. (지금 우리 단계)
- **Lv2** 계약을 **단일 SSOT에서 생성** — `openapi.yaml`을 진실로 두고 `openapi-typescript`로 TS 타입 자동 생성. 사람은 한 곳만 수정.
- **Lv3** **Zod**(또는 typebox)로 스키마를 한 번 정의 → `z.infer`로 정적 타입 + 같은 스키마로 **런타임 검증**. "타입"과 "유효성 검사"가 한 소스.

**드리프트(drift)** = 같은 계약의 사본들이 서로 어긋나는 것. 우리 프로젝트에 실제로 `MeetingStatus`가 **손으로 쓴 세 곳**(openapi.yaml · `@whenwe/types` · prisma schema)에 중복돼 있다(그래서 "값은 @whenwe/types와 일치" 주석을 단다 = 사람이 수동으로 맞추는 중이라는 증거).

**왜 / 트레이드오프**
- **"단일 SSOT에서 생성 → 드리프트 0"의 의미**: 하나를 진실로 정하고 나머지를 *자동 생성*하면, 맞출 사본이 애초에 없으니 어긋날 수가 없다. "사람이 두 번 안 씀".
- 이상(Lv2~3)은 **비용**이 든다: 코드젠/빌드 스텝/규율. 2인 MVP·포트폴리오엔 **Lv1이 합리적**.
- **시니어다움 = 이상을 알고, 지금 그걸 살지 말지 판단하는 것.** "왜 Lv3 안 갔나"를 설명할 수 있는 게 실력 어필.
- 우리는 이미 `openapi.yaml`이 있어 **Lv1 → Lv2 승급 경로가 열려 있다**(손으로 쓰는 게 귀찮아지는 순간 갈아타기). "의도적으로 단순하게 시작하고 필요할 때 승급"(단순성 최우선과 일치).
- 처음부터 합의된 잘 만든 프로젝트라면 애초에 **대소문자/`EXPIRED`/`pending` 충돌이 안 생긴다**(규약을 1일차에 고정). 우리 충돌은 "따로 자란 두 타입을 물려받은" 산물.

**💬 면접 포인트**
"같은 계약을 여러 곳에 손으로 복제하면 드리프트가 불가피해서, 이상적으론 OpenAPI나 Zod를 SSOT로 두고 타입을 생성합니다. 다만 규모상 지금은 손으로 쓴 공유 패키지(Lv1)로 가고, OpenAPI 스펙이 이미 있으니 필요해지면 코드 생성으로 승급할 수 있게 길을 열어뒀습니다."

# 학습 노트 (이어서) — 첫 수직 슬라이스: 비회원 초대 진입

오전의 타입 '설계'를 실제 코드로 옮긴 첫 수직 슬라이스(DB→API→어댑터→화면)에서 배운 것.

## 4. 수직 슬라이스(vertical slice)로 시작한 이유

**무엇**
"백엔드 전부 → 그다음 프론트 전부"가 아니라, **한 기능(비회원 초대 진입)을 DB·API·어댑터·화면까지 얇게 관통**하는 단위로 첫 작업을 잡았다. 엔드포인트 1개(`GET /api/invites/{token}`) + 화면 1개.

**왜 / 트레이드오프**
- API 연결(2층)은 **붙일 대상(백엔드)이 있어야** 검증된다. 그냥 어댑터만 만들면 "허공에 코드"라 end-to-end 검증 불가.
- 슬라이스로 가면 **공통 인프라(응답 봉투·API 클라이언트·어댑터 패턴)를 첫 슬라이스에서 깔고**, 이후 기능은 그 위에 얹기만 하면 된다. 첫 슬라이스가 비싸고 다음이 싸진다.
- 인증이 필요 없는 비회원 조회를 첫 타자로 골라 **전제(로그인) 없이 가장 빨리 "실데이터가 흐른다"** 에 도달.

**💬 면접 포인트**
"레이어별로 쌓지 않고 기능 하나를 끝까지 관통하는 수직 슬라이스로 시작해, 공통 인프라를 조기에 검증하고 이후 기능의 한계비용을 낮췄습니다."

## 5. 공통 응답 봉투 — 인터셉터 + 예외 필터 (cross-cutting)

**무엇**
계약상 모든 응답은 `{ success, data, error }` 봉투. 이를 엔드포인트마다 손으로 감싸지 않고 **NestJS 전역 인터셉터**(성공 → `{success:true,data,error:null}`)와 **전역 예외 필터**(도메인 예외 → `{success:false,...,error:{code,message}}` + HTTP status)로 한 번에 처리. 서비스는 `DomainException(ErrorCode, status)` 만 던진다.

**왜 / 트레이드오프**
- 봉투는 **횡단 관심사(cross-cutting)** — 모든 엔드포인트에 반복된다. 인터셉터/필터로 모으면 컨트롤러는 순수 데이터만 반환(관심사 분리).
- 이건 "투기적 추상화"가 아니다 — 계약이 *모든* 응답에 요구하는 보편 규칙이라 첫 엔드포인트부터 정당.
- `ErrorCode` 를 `@whenwe/types` 에서 공유 → 던지는 쪽(BE)과 분기하는 쪽(FE)이 같은 코드 집합.

**💬 면접 포인트**
"응답 포맷·에러 변환 같은 횡단 관심사는 NestJS 인터셉터/예외 필터로 중앙화해 컨트롤러를 순수하게 유지하고, 에러 코드는 공유 타입으로 FE까지 일관시켰습니다."

## 6. SSR 어댑터의 타임존 버그 — 서버 TZ '박제' (독립 리뷰가 잡음)

**무엇**
마감 시각 라벨을 어댑터에서 `format(new Date(iso), ...)` 로 만들었는데, 이 어댑터는 **서버 컴포넌트(SSR)** 에서 실행된다. `new Date`/`format` 은 **실행 런타임의 로컬 TZ**를 쓴다 → 배포 서버(보통 UTC)에서 포맷되면 모든 사용자에게 KST 23:59가 **14:59로 박제**된다(9시간 오차).

**왜 / 트레이드오프**
- "타임존은 브라우저가 알아서"라는 통념은 **CSR 기준**. SSR에선 포맷이 서버에서 굳어 사용자 TZ와 무관해진다 — 헷갈리기 쉬운 지점.
- 날짜 중 `startDate`/`endDate`(YYYY-MM-DD)는 문자열 split으로 처리해 TZ 무관했는데, `responseDeadline`(date-time)만 `new Date` 를 타서 문제. **같은 어댑터 안에서 날짜 처리 방식이 갈리면 위험.**
- 해결: 한국 서비스이므로 `date-fns-tz` 의 `formatInTimeZone(iso, 'Asia/Seoul', ...)` 로 **고정 TZ**. 실행 환경과 무관하게 결정적.
- 더 근본적으로 "마감 시각을 누가/어디 TZ로 포맷하느냐"는 **직렬화 정책** 문제 — BE가 오프셋(+09:00)을 줄지, FE가 고정 TZ로 표시할지 합의 필요.

**💬 면접 포인트**
"SSR에서는 날짜 포맷이 서버 타임존으로 고정된다는 점을 놓쳐, 마감 시각이 배포 서버(UTC) 기준으로 9시간 어긋날 뻔했고, 고정 타임존 포맷(date-fns-tz)으로 결정적이게 만들었습니다."

## 7. 슬라이스가 '계약 갭'을 드러냄 — 계약은 진화한다

**무엇**
화면이 표시하는 필드(`category`·`durationHours`·선택 시간대)가 **계약(`InvitePublic`)에 없었다.** 슬라이스를 관통하면서 발견 → 계약(openapi + `@whenwe/types`)을 먼저 확장하고 BE·FE가 그 위에 맞춤.

**왜 / 트레이드오프**
- 계약(SSOT)은 고정된 게 아니라 **실제 화면/도메인 요구가 드러날 때 진화**한다. 단, 진화는 항상 **SSOT(openapi/types)를 먼저 바꾸고** 양쪽이 따라가는 순서로 — 코드부터 바꾸면 드리프트.
- 단, 표시용 파생(예: "평일/주말" 구분)처럼 **DB에 없는 화면 전용 값은 계약에 넣지 않는다**(2층 원칙). 실제로 모델엔 단일 시간창만 있어 라벨도 단일창으로 단순화.

**💬 면접 포인트**
"수직 슬라이스가 계약의 누락 필드를 드러냈고, 코드가 아니라 SSOT(OpenAPI·공유 타입)를 먼저 확장한 뒤 양쪽을 맞춰 드리프트 없이 계약을 진화시켰습니다."

## 8. 독립 코드 리뷰를 분리한 효과 (프로세스)

**무엇**
구현자(메인 세션/구현 에이전트)는 자기 코드를 최종 검수하지 않고, **별도 code-reviewer 에이전트**가 계약 정합성·도메인 규칙·정확성을 검수. 이번에 SSR 타임존 버그(6번)와 에러 종류 미구분을 리뷰가 잡았다.

**왜 / 트레이드오프**
- 구현자는 자기 가정에 눈이 멀기 쉽다(타임존 버제는 로컬 KST에선 멀쩡히 보였다). **제3자 관점 + 컴파일된 산출물 직접 검사**가 자기검토가 못 잡는 걸 잡는다.
- 비용: 리뷰 왕복. 하지만 계약/도메인이 걸린 작업에선 회귀를 조기에 막는 값이 더 크다.

**💬 면접 포인트**
"구현과 리뷰 주체를 분리해, 구현자가 로컬 환경 때문에 못 보던 SSR 타임존 회귀를 독립 리뷰가 컴파일 산출물 검사로 잡아냈습니다."

# 학습 노트 (이어서) — REST vs RESTful, 그리고 의도적 일탈

API가 "openAPI 계약과 맞는지 / RESTful한지" 점검하며 정리한 개념과 우리 설계 결정.

## 9. REST vs RESTful — 헷갈리는 개념 정리

**무엇**
- **REST**: Roy Fielding이 정의한 *아키텍처 스타일*(제약들의 집합) — 리소스 중심, 무상태(stateless), 통일된 인터페이스(URI+HTTP 메서드), 표현(representation) 전송, HATEOAS(하이퍼미디어).
- **"RESTful"**: 그 스타일을 *얼마나 따르는지*를 가리키는 형용사. 실무에서 "RESTful API"라 부르는 것 대부분은 **순수 REST가 아니라 "REST 관례를 상당히 따르는 실용 API"**다.
- **Richardson 성숙도 모델**(REST를 얼마나 지키나 4단계):
  - **L0** 단일 엔드포인트로 다 처리(RPC, 예: 하나의 `/api`에 POST).
  - **L1** 리소스 분리(URL이 자원별).
  - **L2** HTTP 메서드 + 상태코드 의미 사용(GET/POST/PUT/DELETE, 200/404/409…). **← 실무 대부분이 여기.**
  - **L3** HATEOAS(응답에 다음 가능한 행동 링크 포함). 거의 안 씀.

**왜 / 트레이드오프**
- "RESTful이냐"는 0/1이 아니라 **정도(스펙트럼)** 의 문제. "우리 API는 Level 2 실용 REST"처럼 위치를 말할 수 있어야 정확.
- L3(HATEOAS)는 이론상 이상적이나 클라이언트 복잡도·오버헤드 커서 실무 효용이 낮다 → 의도적으로 안 가는 게 표준.

**💬 면접 포인트**
"REST는 0/1이 아니라 Richardson 성숙도 모델의 스펙트럼으로 보고, 저희 API는 리소스·HTTP 메서드·상태코드를 지키는 Level 2 실용 REST이며 HATEOAS(L3)는 효용 대비 비용 때문에 의도적으로 두지 않았습니다."

## 10. 우리 프로젝트가 순수 REST에서 '의도적으로' 벗어난 지점 — 이유와 장점

**무엇 + 왜 + 장점** (각 일탈을 "왜 택했고 무엇을 얻는가"로)

1. **응답 봉투 `{ success, data, error }`**
   - 순수 REST: HTTP 상태코드 + 바디 직접. 봉투는 `success`로 상태를 바디에 *중복*하므로 비순수.
   - 이유/장점: **클라이언트가 모든 응답을 한 가지 모양으로 처리**(성공/실패 분기, 에러 코드 추출)할 수 있어 FE 코드가 단순·일관. `ApiResponse<T>` 한 타입으로 FE·BE가 공유. 에러를 도메인 코드(`INVITE_TOKEN_EXPIRED`)로 실어 **국제화/분기**가 쉬움.
   - 비용: HTTP 상태와 `success`가 이중 표현(동기화 책임).

2. **액션 엔드포인트 `POST /meetings/{id}/confirm`**
   - 순수 REST: `PATCH /meetings/{id}` + `{status:CONFIRMED}` (상태도 리소스 속성).
   - 이유/장점: **상태 전이에 부수효과·권한·검증이 얽힐 때** 동사 엔드포인트가 의도를 명확히 드러내고, "확정"이라는 도메인 행위를 한 곳에 캡슐화. 단순 속성 PATCH로 표현하면 "어떤 전이가 허용되는지" 규칙이 흩어짐.
   - 비용: REST 순수성↓(동사 URL).

3. **`POST /availability` 가 사실상 전체 교체(스냅샷)**
   - 순수 REST: 멱등 교체면 `PUT`이 더 정확.
   - 이유/장점(현 상태): 계약이 POST로 고정. 다만 **제출=참여자 응답 스냅샷 교체**로 구현(빠진 슬롯 삭제)해 **멱등성**은 확보 → 같은 제출 반복해도 결과 동일(더블클릭·재시도 안전).
   - 메모: 의미론적으론 PUT 후보. 계약 다듬을 때 고려 대상.

4. **`GET /availability/me`** — `me`는 RPC틱하지만 GitHub `/user` 처럼 **인증 컨텍스트 단축**으로 흔함. 토큰 주인의 리소스를 id 없이 가리켜 클라이언트 단순화. 허용 범위.

**공통 교훈**
- 일탈은 **"몰라서"가 아니라 "알고 택한 트레이드오프"** 여야 한다. 각 일탈이 **무엇을 포기하고 무엇을 얻는지** 말할 수 있으면 그게 곧 REST를 제대로 이해했다는 증거.
- 계약(OpenAPI)을 SSOT로 두면 이런 결정이 **명세에 박제**되어 FE·BE가 같은 규칙을 공유 → 일탈조차 일관되게 적용됨.

**💬 면접 포인트**
"순수 REST에서 응답 봉투·`/confirm` 액션·POST 스냅샷 교체로 의도적으로 벗어났는데, 각각 클라이언트 처리 일관성·상태전이 캡슐화·멱등 안전성을 얻기 위한 트레이드오프였고, 어디서 왜 벗어났는지를 OpenAPI 계약에 명시해 일관성을 유지했습니다."

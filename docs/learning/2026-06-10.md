# 학습 노트 — 2026-06-10

프론트(원격) UI와 백엔드(로컬) 모노레포, 두 갈래를 합치며 정한 **타입 설계 결정**과 그 근거.

---

## 1. 두 갈래 통합 — "무엇을 기준으로 삼을지" 판단

**무엇**
같은 프로젝트가 두 갈래로 갈라져 있었다 — 원격(프론트 담당자: 디자인+UI, 평평한 단일 Next 앱)과 로컬(나: 백엔드까지 염두에 둔 pnpm 모노레포). git 히스토리상 **공통 조상이 없어서**(merge-base 없음) 단순 머지가 불가능했다.

**왜 / 트레이드오프**
- 항목별로 "어느 쪽이 진실인가"를 따로 판단했다: **구조=로컬**(모노레포 — 백엔드를 둘 자리가 있음), **디자인/UI=원격**(담당자 결과물), **패키지매니저=로컬(pnpm)**.
- 핵심 원칙: **패키지매니저는 "디자인"이 아니라 "구조" 선택**이다. 모노레포 워크스페이스(`workspace:*` 내부 패키지 참조)를 쓰려면 pnpm이 필요 → 구조 결정에 종속된다. 그래서 "원격 것을 가져오되 설치만 pnpm으로".
- 안전장치: 합치기 전에 로컬을 `develop-backend` 브랜치로 푸시해 **백업부터 확보**(force-push로 원격 14커밋을 날리는 사고 방지).

**💬 면접 포인트**
"두 갈래를 합칠 때 통째로가 아니라 *축별로*(구조/디자인/툴체인) 진실의 출처를 나눠 판단했고, 패키지매니저는 디자인이 아니라 구조 결정에 종속된다고 봤습니다."

## 2. 타입 2층 구조 — 계약(contract) vs 화면(view-model)

**무엇**
같은 도메인을 설명하는 타입이 두 개였다.
- 원격 `src/types/meeting.ts` — **화면용**(느슨): 소문자 enum(`available`), `id: string`, **이미 포맷된 표시 필드**(`dateRange: "6.1 — 6.14"`, `when: "6.8 (토) 오후 2:00"`).
- 로컬 `@whenwe/types` — **API 계약용**(엄격, SSOT): 대문자 enum(`AVAILABLE`), `id: number`(DB와 일치), `ApiResponse`/`ErrorCode` 봉투.

해결: **2층으로 분리**한다. **계약 타입**(`packages/types`, 백엔드 소유, 네트워크를 건너는 날것 — ISO 날짜·Int id·대문자 enum) + **화면 타입**(`apps/web`, 프론트 소유, 포맷된 표시 형태) + **경계의 변환 함수(어댑터)**.

**왜 / 트레이드오프**
- **표시 문자열을 계약에 넣으면 안 된다.** 서버는 `startAt`(ISO)만 주고 포맷팅(`"6.8 (토)"`)은 프론트 책임. 이걸 계약에 넣으면 백엔드 계약이 화면 사정에 오염된다.
- 2층은 **팀 분업과 정확히 겹친다**: 백엔드는 계약만 책임, 프론트는 화면+어댑터. 서버 응답이 바뀌면 `@whenwe/types`가 바뀌고 → 프론트 어댑터에서 **컴파일 에러로 즉시 드러남**(모노레포+공유타입의 본전).
- **과하게 짓지 않기**: 화면마다 view-model 타입+매퍼를 강제하면 과한 추상화. → "정신은 2층, 구현은 린". 계약 타입을 직접 받아 가장자리에서 포맷 헬퍼 몇 개로 처리하고, **모양이 진짜 갈리는 곳에서만** view-model을 둔다. 과한 레이어도 똑같이 냄새다.
- **지금은 reconcile 미루기**: UI가 아직 mock 데이터라, 원격 화면 타입을 그대로 두고 대소문자·`pending`(미응답=화면 개념)·`EXPIRED` 변환은 **실제 API 연결 시 한 화면씩** 어댑터에서 흡수. 지금 합치면 기능 이득 없이 코드만 흔들림(YAGNI).

**💬 면접 포인트**
"전송 계층(DTO)과 표현 계층(view-model)을 분리하고 경계에 어댑터(anti-corruption layer)를 뒀습니다. 표시용 포맷 문자열이 API 계약에 새어 들어가지 않게 한 게 핵심이고, 다만 규모에 맞춰 매퍼를 남발하지 않고 린하게 유지했습니다."

## 3. 타입 설계 수준 — 드리프트와 "단일 SSOT에서 생성"

**무엇**
타입 설계를 수준별로 정리.
- **Lv0** 각자 타입 → 드리프트가 런타임에 터짐.
- **Lv1** 손으로 쓴 공유 계약 + 화면 변환 → 드리프트가 *컴파일*에 잡힘. (지금 우리 단계)
- **Lv2** 계약을 **단일 SSOT에서 생성** — `openapi.yaml`을 진실로 두고 `openapi-typescript`로 TS 타입 자동 생성. 사람은 한 곳만 수정.
- **Lv3** **Zod**(또는 typebox)로 스키마를 한 번 정의 → `z.infer`로 정적 타입 + 같은 스키마로 **런타임 검증**. "타입"과 "유효성 검사"가 한 소스.

**드리프트(drift)** = 같은 계약의 사본들이 서로 어긋나는 것. 우리 프로젝트에 실제로 `MeetingStatus`가 **손으로 쓴 세 곳**(openapi.yaml · `@whenwe/types` · prisma schema)에 중복돼 있다(그래서 "값은 @whenwe/types와 일치" 주석을 단다 = 사람이 수동으로 맞추는 중이라는 증거).

**왜 / 트레이드오프**
- **"단일 SSOT에서 생성 → 드리프트 0"의 의미**: 하나를 진실로 정하고 나머지를 *자동 생성*하면, 맞출 사본이 애초에 없으니 어긋날 수가 없다. "사람이 두 번 안 씀".
- 이상(Lv2~3)은 **비용**이 든다: 코드젠/빌드 스텝/규율. 2인 MVP·포트폴리오엔 **Lv1이 합리적**.
- **시니어다움 = 이상을 알고, 지금 그걸 살지 말지 판단하는 것.** "왜 Lv3 안 갔나"를 설명할 수 있는 게 실력 어필.
- 우리는 이미 `openapi.yaml`이 있어 **Lv1 → Lv2 승급 경로가 열려 있다**(손으로 쓰는 게 귀찮아지는 순간 갈아타기). "의도적으로 단순하게 시작하고 필요할 때 승급"(단순성 최우선과 일치).
- 처음부터 합의된 잘 만든 프로젝트라면 애초에 **대소문자/`EXPIRED`/`pending` 충돌이 안 생긴다**(규약을 1일차에 고정). 우리 충돌은 "따로 자란 두 타입을 물려받은" 산물.

**💬 면접 포인트**
"같은 계약을 여러 곳에 손으로 복제하면 드리프트가 불가피해서, 이상적으론 OpenAPI나 Zod를 SSOT로 두고 타입을 생성합니다. 다만 규모상 지금은 손으로 쓴 공유 패키지(Lv1)로 가고, OpenAPI 스펙이 이미 있으니 필요해지면 코드 생성으로 승급할 수 있게 길을 열어뒀습니다."

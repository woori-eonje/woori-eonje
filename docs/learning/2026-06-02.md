## 1. 아키텍처: 모노레포 + FE/BE 분리

- **구성**: pnpm workspace 모노레포 — `apps/web`(Next.js) · `apps/api`(NestJS) · `packages/types`(공유 타입)
- **왜 분리(NestJS 독립 백엔드)?** 추천 계산·상태머신·스케줄러 같은 "묵직한 도메인 로직"이 있어 화면 코드와 섞이면 안 됨. + 응답 마감 자동전환 **스케줄러가 24시간 상시 서버**를 요구 → 서버리스(Vercel)에 백엔드를 두지 않음
- **왜 모노레포?** FE/BE가 **타입을 공유**(`packages/types`)해 계약 위반을 컴파일 단계에서 잡고, API 변경을 **한 PR**에서 처리. "분리의 장점(구조화) + 분리의 단점(타입 불일치) 제거"
- **의도적 제외(오버엔지니어링 방지)**: Redis, 메시지 큐, MSA, DDD/헥사고날 → 전부 트래픽 커질 때의 2차 항목

> 💬 **면접 포인트**: "모노레포는 한 사람이 아니라 한 저장소를 뜻하고, FE/BE 담당이 달라도 가능하다. 우리는 계약 공유 이점 때문에 폴리레포 대신 모노레포를 택했다."

## 2. 렌더링: SSR vs CSR, 그리고 트렌드

- **SSR**(서버가 HTML 완성): 첫 로딩 빠름, SEO/공유 미리보기 ✅ → 랜딩·초대 페이지
- **CSR**(브라우저가 렌더): 인터랙션 부드러움 → 슬롯 선택·추천 결과 화면
- **2026 트렌드**: "둘 중 하나"가 아니라 **서버 우선(SSR/RSC) + 필요한 곳만 CSR**. 이유 ① 첫 화면 속도(Core Web Vitals) ② SEO ③ JS 전송량 감소

> 💬 **면접 포인트**: "CSR(SPA) 전성기 → 서버 우선으로 회귀. RSC·스트리밍으로 페이지 내에서 서버/클라이언트를 섞는 게 핵심."

## 3. 계층 개념 정리 (헷갈리기 쉬움)

```
NestJS / Next.js   ← 프레임워크 (구조)
TypeScript         ← 작성 언어
JavaScript         ← 실제 실행 언어 (TS는 JS로 컴파일됨)
Node.js            ← 실행 환경(런타임)
```
- Next.js = 프론트(React 기반), NestJS = 백엔드. 이름만 비슷할 뿐 역할 반대.
- 둘 다 "Node.js 위에서 / TypeScript로" 작성 → 경쟁이 아니라 **계층**.

## 4. Prisma 7 (구버전과 다른 핵심 변경)

- **연결 URL을 `schema.prisma`에 못 둠** → `prisma.config.ts`로 분리 (`.env`는 dotenv로 로드)
- **런타임 드라이버 어댑터 필수**(Rust 엔진 제거) → `@prisma/adapter-pg` + `pg`로 `new PrismaClient({ adapter })`
- NestJS 연동: `PrismaService extends PrismaClient`(onModuleInit에서 `$connect`) + 전역 `PrismaModule`
- **ORM = SQL을 코드로** 다루게 해주는 것 (Prisma = TS판 JPA). 스키마 한 파일 → 타입·마이그레이션·쿼리 일원화

> 💬 **면접 포인트**: "Prisma 7은 Rust 엔진을 빼고 드라이버 어댑터 방식으로 전환됐다. 그래서 PrismaClient에 pg 어댑터를 주입해야 한다."

## 5. API 협업: 설계-퍼스트 & OpenAPI

- **코드-퍼스트**(코드→문서 자동생성) vs **설계-퍼스트**(명세 먼저 합의→구현). **FE/BE 담당이 다르면 설계-퍼스트**가 유리 — 명세가 언어 중립이라 FE가 BE 코드 안 봐도 됨, 병렬 개발 가능
- **OpenAPI = 규격(명세 포맷)**, **Swagger = 그 규격을 다루는 도구**(Swagger UI 등). 원래 Swagger 명세 → OpenAPI로 표준화됨
- **SSOT는 하나만**: 설계-퍼스트면 OpenAPI 명세가 진실 → FE는 거기서 타입 생성(openapi-typescript), mock 서버(Prism)로 병렬 개발
- 문서 HTML은 **YAML에서 도구가 자동 생성**(`redocly build-docs`) — 손으로 안 만들고 커밋도 안 함

> 💬 **면접 포인트**: "계약을 단일 출처로 두는 게 핵심. 출처가 둘이면(코드+명세) 반드시 어긋난다."

## 6. OpenAPI 읽는 법

- 엔드포인트 = `경로 + HTTP 메서드`
- **입력(파라미터)** 위치 2곳: `parameters`(경로/쿼리/헤더) · `requestBody`(본문 JSON)
  - 파라미터 4요소: `name` / `in`(path·query·header) / `required` / `schema`(타입)
- **응답**: `responses` 아래 **HTTP 상태코드별**. 2xx=성공, 4xx=에러
- **`$ref`** = 재사용 포인터("저기 정의를 끼워 넣어라"). `#`=현재 파일 루트. 중복 제거 + 한 곳만 고치면 전부 반영
- **`allOf`** = 여러 스키마를 합친 모양

## 7. API 설계 패턴 (도메인에서 쓴 것)

- **공통 응답 봉투**: `{ success, data, error }` — 성공/에러 일관 포맷. 실제 데이터는 항상 `data` 안
- **에러코드 enum** 중앙화 → FE/BE가 같은 코드 공유
- **토큰 2종 분리**: `invite_token`(모임 접근) vs `participant_edit_token`(내 응답 수정) — 역할이 다르면 토큰을 나눈다
- **상태머신**: `DRAFT→COLLECTING→READY_TO_CONFIRM→CONFIRMED→CLOSED`, 상태별 액션을 **서버에서 강제**
- **동시성**: `(participant_id, slot_id)` unique + 재제출은 upsert / 확정은 **조건부 UPDATE**(`WHERE status IN (...)`)로 중복 방지

> 💬 **면접 포인트**: "낙관적 동시성 — 유니크 제약 + upsert로 중복 응답을, 조건부 UPDATE로 중복 확정을 막았다."

## 8. CustomException vs API 명세

- 예외는 **내부 구현**, 명세는 **외부 계약** → 분리된 개념
- CustomException 클래스 자체는 명세를 바꾸지 않음. **새 에러를 외부에 노출할 때만** 명세(ErrorCode enum + responses) 갱신
- 설계-퍼스트 순서: **명세 먼저 → 예외 구현**. CustomException의 code는 명세 ErrorCode와 일치해야 함
- NestJS 패턴: CustomException(code+message+status) → 전역 ExceptionFilter가 `{success:false,data:null,error}` 봉투로 직렬화

- **monorepo 협업**: FE는 `apps/web`, BE는 `apps/api`, 각자 `feature/*` 브랜치 → 같은 레포에 PR

## 10. TDD vs DDD (자주 헷갈리는 비교)

- **핵심: 경쟁 관계가 아니라 직교(다른 축).** DDD = 도메인을 *어떻게 설계/모델링* 하는가(구조 방법론), TDD = 코드를 *어떤 순서로 작성* 하는가(테스트 먼저 워크플로). "DDD 대신 TDD"가 아님 — 둘 다/하나만/둘 다 안 함 가능.

### TDD의 단점 (장점만 있지 않다)
- 탐색적·요구 불명확 작업(프로토타이핑)에선 **초기 속도 저하**, 오히려 방해
- 설계가 출렁이면 **테스트도 재작성**(테스트도 유지보수 대상)
- 잘못하면 **구현 디테일에 결합된 테스트** → 리팩터링 시 멀쩡한 코드인데 다 깨짐(가장 흔한 실패)
- **커버리지 착시** — 테스트 있다고 옳은 게 아님
- UI/CSS, 써드파티 통합, 동시성·성능엔 단위 TDD가 잘 안 맞음
- 단순 CRUD 보일러플레이트엔 ROI 낮음(전면 적용 과함)

### TDD의 장점
- **복잡한 순수 로직**(추천 알고리즘 등)엔 최고 — 테스트가 곧 실행 가능한 명세 + 회귀 방지
- "테스트하기 쉽게" → 자연히 **결합도 낮은 설계**
- 버그 재현 → 수정 → 영구 회귀 방지 루프

### 언제 각각 비싸지나
- **DDD**: 도메인이 단순하면 과함(Aggregate/VO/Bounded Context 오버엔지니어링)
- **TDD**: 요구 불명확/탐색적·단순 CRUD에선 비효율

### 이 프로젝트 결론 — "선택적 TDD"
- DDD는 도메인이 작아 제외. 같은 논리로 **TDD도 전면 X → 비싼 가치 나오는 곳에만**.
- 추천 알고리즘·상태머신·토큰 = TDD / 단순 CRUD = test-after·가벼운 통합테스트
- 원칙: **구현 디테일이 아니라 "행동(behavior)"을 테스트** → 리팩터링 내성 확보

> 💬 **면접 포인트**: "DDD와 TDD는 직교하는 개념이다. 도메인이 작아 DDD는 오버엔지니어링이라 뺐지만, 추천 알고리즘처럼 복잡·결정론적 순수 로직엔 TDD로 명세를 박제했다. TDD의 함정은 구현에 결합된 테스트라, 행동 중심으로 짜서 리팩터링 내성을 지켰다."
